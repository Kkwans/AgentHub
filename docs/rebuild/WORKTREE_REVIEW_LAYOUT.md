# Worktree 审阅主内容布局

## 证据与目标

2026-11-14 00:44–00:45 UTC 人工复核89ae0b7运行43532719381真实浏览器四视口截图。1440/1024宽屏在滚到确认按钮后，中央主要空间空白，实际审阅挤在340–430px右栏；768单栏反而更可读。截图在确认勾选且按钮enabled后、POST之前，不是pending状态。原布局1.45fr/0.82fr优先给短任务列表分配空间；AppShell main独立滚动导致任务上下文离开视口。

目标：延续用户选择的Codex中性视觉，审阅时让内容成为主区、任务列表作为紧凑导航。不扩大本片为整个工作台重构。

## 实施边界

- 仅选中Worktree处于REVIEW或原操作锁仍有效时启用主审阅布局。
- >=1024px：列表clamp(240px,22vw,280px)，审阅minmax(0,1fr)；列表仅保留标题/状态。
- 列表可滚动并sticky；主审阅取消整卡sticky和overflow hidden，紧凑任务标题保持sticky。长description放在标题下，避免固定上下文占满视口。
- <=1023px保留既有单栏、返回列表、选择锁及路由语义。
- 合并为filled主按钮，读取和返工仍为次操作；未知结果保护、重新读差异和明确勾选全部保留。
- 不改变WorktreeReviewActions key或挂载条件，不重建owner，不更改服务端Git合同。

## 验收

1. 普通Task布局不变，Worktree REVIEW/MERGING/unknown保持同布局身份。
2. 既有生命周期、双核对入口、跨路由与授权切换回归继续通过。
3. 真实retry浏览器四宽保存初始审阅与重新确认截图；桌面列表230–290px、审阅至少列表2倍宽，滚动到合并后标题仍可见且不覆盖按钮。
4. 390/768不横溢出，原确认/重试/真实Git结果断言不弱化。
5. 本地Chromium仍因AF_UNIX权限不可启动，使用精确新提交CI运行后取回截图逐张验收；静态构建、测试发现和旧截图均不能当新视觉通过。

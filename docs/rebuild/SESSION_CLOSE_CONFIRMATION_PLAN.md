# Session 逻辑关闭与资源停止确认方案

状态：只读审查结论与待实施设计。本文不是产品修复，不代表新增字段、接口行为或测试已经落地。

## 1. 已确认事实与风险分级

审查对象：`SessionService.closeAdmitted`、`closeHandleStrictly`、`closeHandleSafely`、shutdown、continuation，以及 Workspace 状态文案。

| 路径 | 当前行为 | 能证明什么 |
| --- | --- | --- |
| 用户关闭有活动 handle 的 Session | detach 后尝试 close；`closeHandleSafely` 吞掉拒绝/超时，随后持久化 CLOSED 并返回成功 | 本地会话逻辑关闭，不证明外部进程或连接停止 |
| 再次关闭该 Session | 原 handle 已 detach，可能直接返回 CLOSED | 不会重新确认此前失败的资源清理 |
| 未确认资源清理 | handle 留在 `unconfirmedHandles`；shutdown 保持失败 | 不允许基于健康停服路径释放运行时独占权 |
| 后续会话准入 | strict close 失败本身不统一设置 `acceptingTaskStarts=false`；`resourceCleanupUnconfirmed` 的专用错误处理在资源获取路径 | 不能声称所有新会话准入已被关闭 |
| 续接 CLOSED Session | 服务端检查 blocking Run，并拒绝任务会话独立续接；普通无 blocking Run 的会话仍可创建新的 handle | 已有未决 Run/任务保护仍有效；资源清理未知尚未独立参与续接决策 |
| Workspace 文案 | “Session 已关闭”“历史记录仍可查看，但已关闭的 Session 不能继续发送指令”，并提供“基于此上下文继续” | 没有直接宣称 Agent 已停止，但逻辑关闭与资源确认尚未清晰区分 |

**当前结论是返回状态与资源确认的表达缺口，不是已证实的新 P0。** 未证明失败 close 会健康释放运行时锁，也未证明该路径已造成重复派发。不能把“仍可能保留外部资源”扩大为“外部 Agent 确实仍在执行”。多个 handle 本身也不是重复派发证据。

已有 shutdown 的保守边界必须保留。若后续获得实际资源继续写入、准入绕过或重复副作用证据，应单独记录复现并重新评级。

## 2. 最小产品合同

将两个概念分开：

- `status=CLOSED`：本地 Session 不再接受指令，历史保留。
- 资源清理结果：只陈述服务端掌握的清理证据，不由 CLOSED、detach、没有 active handle、超时、重启或重复请求推断。

候选结果语义：

| 结果 | 含义 |
| --- | --- |
| `CONFIRMED` | 对适用的资源清理合同取得明确成功结果；不能扩大为对外部所有后台任务的全面停止证明 |
| `UNKNOWN` | 已尝试清理但拒绝、超时或确认记录不完整；不得自动变成成功 |
| `NOT_OBSERVED` | 历史记录或本实例没有足够的资源清理证据；没有 handle 不等于已停止 |

以上名称只是设计候选，不是已有 API 字段。

## 3. Session 级 sticky 元数据与读写合同

建议保存 Session 级清理元数据，关联原 activation/资源身份或不可复用的清理尝试标识；包括结果、记录时间和白名单错误码。不要把原始凭据、provider payload 或不必要的底层错误原文写入公开字段。

1. 在丢失活动资源关联之前，建立可核对的清理尝试记录。清理成功与失败均应指向同一次尝试，不能由较旧回调覆盖新的 Session/activation。
2. UNKNOWN 必须跨重复 close、GET、刷新及服务重启可识别。仅给第一次 close 响应追加警告，不能解决后续请求误判。
3. 重复 close 返回同一未确认结果，不因 active map 为空而提升为 CONFIRMED，也不隐式重新派发 close。是否提供显式再次核对或资源清理操作，应另有明确授权和身份合同。
4. 若资源清理成功但确认持久化失败，结果仍不得报告已确认。保留未确认状态及诊断，不通过“资源大概已经停止”跳过证据缺口。
5. 旧数据缺少清理元数据时显示 NOT_OBSERVED，不批量回填为 CONFIRMED。
6. GET 与 close 响应使用相同的结果解释，避免一次请求警告、刷新后却显示全面成功。

需先确认现有数据库迁移、Session DTO 与生命周期 CAS 的兼容方式，再实施。不要仅将 `closeHandleSafely` 换成严格抛错：首次失败后 handle 已 detach，第二次请求仍可能返回成功。严格错误传播必须与 session 级 sticky 记录一起设计。

## 4. 续接策略与 UI

建议的最小保守策略：对**已知 UNKNOWN**的源 Session，暂不允许通过“基于此上下文继续”隐式绕过资源核对；服务端返回明确的未确认原因，前端保留只读历史和核对说明。现有 blocking Run 与任务会话检查不变。

NOT_OBSERVED 与既有历史会话的兼容策略需要明确决定：不能将无历史证据一律宣称已停止，也不宜未经说明批量破坏旧会话续接。任何允许继续的路径都应解释它将新建会话，而不是确认或恢复原资源。此项是待定产品合同，不表示当前已禁用续接。

不改变生命周期时，可先采用准确的状态解释：

> 本地会话已结束，历史仍可查看；此状态不证明外部 Agent 已停止。

对 UNKNOWN 单独显示：

> 资源停止尚未确认。请先核对原操作，不要把再次关闭视为停止证明。

不显示“Agent 已停止”“清理完成”“安全重试”等超出证据的结论。单独修改文案只能改善解释，不能作为 sticky 状态和续接边界已经修复的证据。

## 5. 必要验证清单

以下测试尚待本方案实施，不得把现有测试通过冒称为本方案验证完成。

- 正常 close：逻辑关闭和清理结果分别正确；确认关联精确 activation/attempt。
- close 拒绝与超时：返回 UNKNOWN，Session 级记录可通过 GET、刷新和重启恢复。
- 重复 close：不重新派发，不把 detach/空 active map 当成功；结果仍 UNKNOWN。
- 迟到回调：旧尝试不能覆盖新 activation 或更新的清理结果；超时后的回包如何收敛必须有明确证据合同。
- 持久化失败：资源已关闭但确认写入失败时，不返回虚假的 CONFIRMED。
- shutdown：未确认资源导致 sticky 失败，数据库与健康运行时独占权不得提前释放。
- 续接：blocking Run、任务会话原有拒绝保持；已知 UNKNOWN 的普通 idle 会话按明确策略拒绝，不创建新 handle。
- 历史无元数据：呈现 NOT_OBSERVED，执行约定的兼容策略，不推断为成功。
- UI：CLOSED 文案、UNKNOWN 提示、禁用/错误原因、刷新一致性及键盘可达；390 等窄视口不挤压主要操作。
- 数据暴露：仅公开白名单状态与安全诊断，不泄露凭据或 provider 原始 payload。

## 6. 实施边界

本文仅记录方案。实施应作为独立逻辑切片，先建立回归证据，再修改持久化/API/UI，并完成相关类型、lint、测试、构建与精确提交的浏览器验证。不得据此自动重放未知操作、释放已有资源 claim、部署、合并 main 或对用户现有 Agent 做故障注入。

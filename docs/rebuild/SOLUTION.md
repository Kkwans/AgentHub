# 详细技术与产品方案

当前视觉状态：用户已否定原整体界面及两轮全部概念；最新要求参考 Codex 的实际 UI，正在基于真实参考重新研究，尚未选定实施稿。下列旧布局/样式建议只是历史技术规划，不构成视觉认可或实施授权；功能真实性与生命周期修复独立推进。

## 1. 目标与取舍

第一目标是普通用户不用理解内部实体即可完成：选择项目 → 确认可用 Agent → 描述工作 → 执行/批准 → 审阅修改 → 完成。第二目标是有设计感、稳定而流畅的桌面工作台，手机能够查看、批准、停止、审阅，不硬挤四栏。

保留 TypeScript 单体及数据库契约，原因是现有适配生态、测试与数据模型可复用。重构重点放在工作流编排、状态归属和 UI。若后续真实 profile 证明框架或存储阻碍目标，再单独 ADR 比较迁移成本、兼容与回滚，不凭主观厌恶换栈。

## 2. 工作创建与恢复协议

- 任务创建成功是独立持久结果；Agent 启动失败不能抹去该结果。
- 明确阶段：draft / creating / created / starting / running / start_failed / outcome_unknown。
- UI 保存服务器返回的 taskId，错误时展示“任务已创建，启动失败”及查看任务/恢复启动，不重新 POST create。
- 服务端启动需要任务级单次受理和状态条件更新；为 clientRequestId 建持久幂等边界时同时定义请求摘要、保留期、冲突响应，不用纯前端按钮禁用冒充幂等。
- 保存用户主目标、补充说明、验收标准，不相互替代。初始 Run 与返工输入应采用同一可测试的上下文构造器。
- 新建任务所选 Prompt 必须生成显式任务绑定或一次性已解析上下文，采用固定版本/内容哈希并存来源；绝不只做 URL 装饰。变量缺失先显示可修复表单。

## 3. 项目与 Agent 就绪

项目选择展示本机/节点、允许根、目录面包屑、仓库候选、Git/写入/Agent 可用性；目录跳转每次都由服务端 containment 校验。Agent 的“已安装”“已注册”“可启动”“需登录”“不可用”分开，READY 不能覆盖最新诊断失败。昂贵发现由用户动作或受控缓存触发，普通列表不反复执行完整扫描。

## 4. 设计系统与信息架构

采用克制的工程工作台：中性灰底、明确层级、少量品牌强调色、真实状态色；不靠大面积渐变、玻璃卡片或数据卡墙营造精致。统一字号、字重、行高、8px 间距体系、圆角、边框、阴影、图标尺寸与动效时长。浅深色分别检查对比度，系统减少动态效果生效。

- 左侧稳定项目/会话导航；主区域只突出当前工作及一个主要操作。
- 首页为继续工作、需要处理和开始入口，不堆领域统计。
- 工作台中心对话/任务进度，审阅区承载文件、Diff、Git；批准与停止始终可达；终端按需展开。
- 1024/768 下审阅区切换 tabs/drawer；390 下内容单列，避免遮挡输入和批准。
- 组件层只保留一套 Button/Input/Dialog/Menu/Tabs/Status/Empty/Error/Loading；逐页迁移而非增加第三套样式。
- 每个页面必须定义 loading/empty/error/partial/stale/disconnected 状态，错误有具体恢复动作。
- 先截图审查当前真实页面，再实现关键首页/项目/Workspace 的视觉样板，以实际浏览器验证后扩散。

## 5. 后端与实时连接

把 SessionService 逐步拆成 SessionLifecycle、RunCoordinator、ApprovalDelivery、Configuration、Continuation 等内部服务，领域类型不依赖协议供应商。每次拆分先保留行为回归。

统一认证主体标识与撤销事件：HTTP、WS、PTY 绑定同一主体；注销/改密/撤销必须停止旧连接，连接建立与撤销竞争也要覆盖。不记录 token 原文；历史事件补流再次校验有效性，输出与重放有容量边界。

## 6. 验证与交付

分四级证据：单元/fixture → 本地真实服务 HTTP/浏览器 → 真实 Agent → NAS。每一级独立标记，不能互相替代。

每切片 lint/typecheck/test/build；涉及流程需故障注入、连点、取消、返回、重连、重启；UI 需 1440/1024/768/390 的实际页面截图、console/pageerror、溢出和关键交互。CI 补 real-service 门禁，不在普通 CI 调用付费 Agent。

保留现有 API 和数据，迁移有前向/回滚说明；禁止重置用户数据库。开发分支逐切片提交，main 合并与实际部署单独作为最终门禁，不能把“同 NCP 工作方式”推导为自动部署许可。

## 7. 审查后确定的关键契约

### 操作身份与结果未知

创建前生成稳定 clientRequestId，绑定 projectId、Agent、Prompt版本、草稿摘要；同一意图重试不能换 ID。服务器记录受理/实体结果并提供只读核对，创建成功但响应丢失时仍可恢复 taskId。相同 ID 不同内容返回冲突，不静默修改。持久幂等完成前，UI 对结果未知仅给核对入口，不假装“再试一次”安全。

关闭创建弹窗只关闭视图，不取消已受理工作；切项目/账号/退出登录后，旧结果不得跳转当前页面或覆盖新草稿。已开始任务的取消是独立服务端动作。流程所有异步结果都核对原目标与草稿版本。

### Prompt 默认语义

本轮选定：新建任务的显式 Prompt 选择在确认预览时解析并固定版本，以任务级 VERSION 绑定保存；Run 保存此次解析的版本、内容哈希与来源。缺变量不启动。返工默认沿用固定版本，用户显式更换时先预览，新版本只影响后续 Run，历史快照不变。既有项目/Agent绑定仍遵守既有优先级，不静默替换。变量如何持久化及敏感字段排除将在 schema 切片详细设计后实施，不直接把任意变量写入日志。

### 导航与完成语义

全局主侧栏稳定；进入项目后出现项目内二级导航，Workspace 会话列表属于该项目情境。分区链接匹配子路由，具体叶子链接精确匹配；前进/后退和旧URL重定向有回归。

Agent 停止输出不代表 Run 成功；Run 成功不代表任务完成。任务先进入待审阅，由用户确认完成。确认完成不隐式 Git 提交或合并。审阅显示测试命令、时间和对应代码快照，旧测试不作为当前代码的验证。

### 可量化验收

先记录基线，再为首次有效工作步骤数、可交互延迟、长会话滚动卡顿、断线恢复耗时设阈值。不要先编造“提升百分比”。视觉首批样板必须包含无Agent、部分成功、批准、断线、长输出、深色和390px；候选字号/间距在真实截图验证前不当作最终标准。


## 8. Session activation提交边界（AH059实施方案）

已发布的resume token负责本次操作归属，但不能替代旧异步消费者最终写入时的归属核对。两条合法竞争已证明旧回调会破坏恢复后新Session状态，因此本片采用每Session、仅本实例的短提交队列。

- resume只把最终READY条件写入、token重验、同步activation登记放入提交区。
- 旧断连消费者在Run写入前、最终Session写入/精确detach前，进入同一队列并重验捕获的activation。
- Task observer、adapter/provider、配置读取、handle.close均留在锁外。close可立即撤销挂起resume，只在最终CLOSED持久化时进入队列。
- 失败不能毒化后续队列；清理只移除自己仍占有的tail。需用真实DB barrier验证旧提交先赢与新activation先赢两种顺序，而非只测check之后没有并发。
- 此处不引入跨进程runtime互斥，不覆盖尚未审查的全部persistEvent/Approval收敛，也不倒推已开始的外部Task observer可撤销。下一阶段若统一所有消费者，应先列写入者与顺序不变量，再决定共享提交接口或持久activation代际，不把零散检查冒充全局事务。


### 8.1 Approval失败与当前工作的隔离（AH060实施约束）

旧决定的UNKNOWN/DEAD是必须保留的历史事实，但不是断开当前Session或关闭当前handle的授权。同一连接也可能已开始下一Run，故仅activationId不能识别归属。

方案以有引用计数的connection epoch lease跨detach保留代际，释放只回收自身；通过DB锁内核对Session归属、latestRunId及Run状态决定当前副作用是否仍适用。Run准入在同一短提交区重新验证READY/active并持久化latestRun，prompt/git/provider在区外。失败提交与精确detach需受同一边界保护，handle.close和Task observer在区外，后续不再盲写Session。

close可在DB await期间撤销归属，因此必须在DB返回后再验；Run创建已持久后再发现失效，须按本次runId走确定未派发的准备失败收敛，不能直接抛409留下QUEUED，也不能误标派发未知。补偿不得把已关闭或被新activation接管的Session改回READY。未取得明确lease不能借“active为空”授权当前资源副作用。此方案仍不代表跨进程runtime协调已完成。

# v0.5 可用性闭环

最后更新：2026-08-11

## 目标

v0.5 不以页面、卡片或 mock 数量作为完成标准。发布必须让普通开发者在不知道 token、
Session ID、Task UUID、Docker 命令或内部状态机的前提下，完成以下真实旅程：

1. 使用管理员账号登录；
2. 按依赖顺序准备 Execution Target、Project 与 Agent；
3. 从 Project 选择兼容且可用的 Agent，创建 Session 并直接进入 Workspace；
4. 发送指令、观察流式结果、处理 Approval、停止或恢复 Session；
5. 查看文件、Diff 与 Git 状态，并对选择的文件创建 commit；
6. 将结果带回 Task 审阅，确认完成或带反馈返工；
7. 通过可搜索对象完成 PromptOS / Skill Binding，而不是手填内部 UUID。

所有用户操作、说明、错误和空状态使用简体中文；Agent、PromptOS、Git、Terminal、模型、
模式、路径、分支、命令、协议和供应商原始数据保留专业名称。

## 现状证据

2026-08-11 已在正式 Compose 部署和真实生产数据上完成 TX5Pro Chrome 150 只读基线审计，
证据见 `docs/qa/tx5pro/2026-08-11-v05-baseline/`。本轮没有伪造 API 或 WebSocket，也没有
执行写请求。

主要阻断项：

- Project 的“打开工作区”指向 `/sessions?projectId=...`，但 Session 页忽略参数且没有新建入口；
- 首次使用的依赖顺序没有表达，Project 需要 Execution Target，Agent 又在另一个页面注册；
- Workspace 除 Session 外的请求失败会被空数组吞掉，可能把 Approval 加载失败显示成无数据；
- Session 事件固定读取最早 500 条，长会话无法继续补流；
- Approval、停止 Run、断线恢复和 PromptOS Context 错误缺少可靠反馈与恢复操作；
- 普通 Session 没有使用后端现有 selected-files commit 能力；
- Task 返工不接受反馈也不会创建下一轮 Run；PromptOS 的 Task Binding 依赖手填 UUID；
- 移动端 Project 操作被隐藏，Task 五列看板被截断，大量触控目标小于 44 px；
- 现有浏览器 E2E 主要拦截 `/api/v1` 使用 fixture，不能证明真实后端业务闭环。

## 产品与交互合同

### 1. 首次使用与引导

- 空数据时显示一条可操作的准备路径：Execution Target → Project → Agent → Session。
- 每一步都必须显示真实状态、缺失原因和唯一明确的下一步，不展示不可执行的假按钮。
- 当前正式部署已有 Target 和 Project 时，从第一个未完成步骤继续，不要求重复配置。
- Docker、container ID、workspace mapping 等高级信息留在 Agent 页，不进入普通 Session 创建表单。

### 2. Project → Session

- Project 的主操作改为“开始会话”，桌面和 390 px 都必须可见。
- `/sessions?projectId=<id>&new=1` 是可分享、可刷新、支持前进后退的创建状态。
- 创建表单只列出与 Project Execution Target 兼容且状态为 `READY` 的 Agent。
- cwd 默认取 Project 的真实根目录；不让普通用户输入任意绝对路径。
- 没有兼容 Agent 时，说明原因并提供“前往 Agent”入口；不得提交一个必然失败的 Session。
- 创建成功后直接进入 `/sessions/:id`，失败必须保留输入并显示可操作的中文错误。

### 3. 服务端安全边界

创建 Session 时服务端必须重新验证：

- Project 存在且为 `ACTIVE`；
- cwd 位于 Project real root 内，且通过 lexical containment 与 symlink escape 防护；
- Agent 存在、启用、状态为 `READY`；
- Agent 与 Project 的 Execution Target 兼容，Docker/Remote 映射在运行前仍有效。

前端筛选仅改善体验，不能替代这些服务端校验。错误使用稳定英文 code，Web 映射中文说明。

### 4. Workspace 可靠性

- Messages、Runs、Events、Approvals、Agent、Project、capability 分区显示 loading/error/retry，
  Approval 请求失败不得伪装为空状态。
- Events 使用 `lastSeq` 增量拉取、合并与去重；WebSocket 首连和重连都携带 cursor。
- Approval 的用户决定、Outbox 和审计事件原子保存；相同决定幂等，不同决定冲突。投递显示
  pending、成功、`UNKNOWN` 或 `DEAD`；没有 adapter 幂等回执时不得盲目重发。
- 停止 Run 防重复提交；取消必须在有限时间内收敛到终态或明确的失败状态。
- `DISCONNECTED` Session 提供“恢复”与“关闭”；关闭和高影响操作复用确认 Dialog。
- PromptOS Context 区分缺变量、无绑定和服务失败，提供重试，不能只显示“异常”。
- 移动检查器复用 Radix Dialog/Sheet，具备 focus trap、Escape、焦点恢复和明确关闭按钮。

### 5. 审阅闭环

- 普通 Session 的 Git 面板提供 status、Diff、历史、分支和 selected-files commit。
- commit 前显示所选文件与提交信息，失败不改变工作区，成功后刷新 status、Diff 与历史。
- 非 Git 或 Remote 不支持的 Project 隐藏无效 Git 操作并说明能力边界。
- Task Review 必须展示 acceptance criteria、Run 与 Git evidence。
- “返工”要求反馈，并以新 Run 或可恢复 Session 进入下一轮，不允许只翻转 Task 状态。
- PromptOS/Skill 的 Task 目标使用可搜索选择器，并按当前 Project 过滤。

### 6. 通用体验与可访问性

- 交互状态写入 URL；刷新、返回、前进和分享链接后保持同一上下文。
- 表单错误关联字段，设置 `aria-invalid` / `aria-describedby`，并聚焦首个错误。
- 动态连接、Run、Approval 与消息使用合适的 `status`、`alert` 或 `log` live semantics。
- 移动端非行内链接的核心触控目标至少 44 × 44 px；输入字号至少 16 px。
- 命令面板实现完整 combobox/listbox 键盘模型；resize handle 必须有可见 focus 样式。
- loading、空、错、断线、认证失效都必须提供下一步或重试，不留死路。

## 状态变更与回滚

- 数据库迁移只向前追加；涉及 Approval 投递状态时先备份正式 PGlite，并记录恢复命令。
- 每个逻辑切片独立 commit；部署前保留当前镜像、Compose 文件与数据库冷备份。
- Compose 仅对 `agenthub` Project 执行 `up -d`，不执行 `down`，不删除镜像、容器或卷。
- 不修改 Claude Code、Hermes、OpenClaw 的 Compose、镜像、挂载或持久数据。
- 出现回归时恢复上一镜像和 Compose 配置，再验证 health、登录、Project、Agent 与既有数据。

## 非目标

- 不新增第二套 UI 框架、Icon 包或设计 token；继续复用 Radix Themes、Phosphor、Tailwind、
  TanStack Query 和现有共享组件。
- 不在本阶段实现多 Agent swarm、Workflow Designer、Marketplace、Memory/RAG、RBAC/SSO、
  完整 Git 客户端或 Docker 镜像管理。
- 不用普通 shell 冒充 Terminal；native PTY 不可用时保持 capability=false。
